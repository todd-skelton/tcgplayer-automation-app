# Reviewed eBay price changes

The slab recommendation panel now saves a price-change preview for one selected listing. Choose the calculated or separately reviewed ask, then save the preview. It records the imported listing snapshot, old/new USD item price, identity/inventory revisions, recommendation, evidence references, policy, seller constraints and review reason. Reopening the listing retrieves its latest saved preview without contacting eBay.

Migration 031 adds one indexed PostgreSQL table. Preview intents are immutable: concurrent retries with the same intent return the first saved plan; reuse for another selection is rejected. Plans expire at the earlier of 15 minutes or their evidence expiry. Reads flag changed inventory, recommendation, identity, comp decisions, evidence or reviewed ask. A new preview is required after changes. Each plan is bounded to 64 KiB; creation removes at most 100 previews expired more than 30 days ago. There is no new dependency, queue, polling loop or always-on worker. The review panel is loaded on demand.

Only active, single-quantity fixed-price listings without variations or unresolved listing reasons can be previewed. A confirmed identity must be assigned to the listing. The recommendation must have a supported policy and adequate direct evidence, with the listing's current USD price and shipping charge. Reviewed overrides must use whole cents and meet saved seller floors; unknown inputs cannot satisfy a requested profit constraint. CSV/manual inventory is supported for preview but is not proof of live seller state.

## Current delivery boundary

The app supports previews and an explicit imported-inventory dry run. Open a saved preview and choose **Run without writing** to record the approval/checking/outcome path without contacting eBay. Reload outcomes or inspect its recorded steps after restarting the app. In-progress dry runs can be resumed using their original intent. `canPublish` remains false: live preparation, approval, write and restore HTTP actions are disconnected until seller access and its concrete adapter are verified. The shared production eBay keyset still needs activation coordinated with the other app that uses it.

Migration 032 adds publication intents and their event ledger. The tested server execution capability accepts a narrow seller reader and price-only writer. A live plan captures the authenticated seller, exact item/variation IDs, certificate, old/new price and protected-field fingerprint. It expires within five minutes or at preview expiry, whichever is earlier. The 16 KiB execution record references its existing immutable preview; it does not duplicate the recommendation/evidence or full preview. History returns 25 summaries and detail reads at most 50 events. Preview retention preserves every referenced preview. Publication outcomes are retained for audit; there is no automatic audit purge.

Only explicit approval can move a prepared live intent into execution. A database constraint permits one approved/unresolved live intent per listing. A 90-second lease fences concurrent and cancelled workers, and every provider operation has a hard 25-second wait bound. The price-write boundary is committed before dispatch. If the process stops after that boundary or a response is uncertain, recovery only reads back: an old price is not proof that a late write cannot still occur, and it never triggers a repeated write. Unresolved intents keep their listing lock and cannot be cancelled as if nothing happened. Reconciliation remains explicitly available after reconnect; no scheduler polls it. A confirmed intent is terminal and retries issue no provider requests. Explicit batches process at most ten intents sequentially and retain per-item failures.

The record becomes confirmed only when a new read verifies the selected price and all protected fields. Acknowledgement alone is insufficient. Seller, item, certificate, availability, quantity, price or protected-field changes before writing produce a conflict; unsupported listing capabilities remain in review. A requested restore uses a new current preview selecting the original intent's prior price, its own approval, conflict check and readback. It links to the original confirmed outcome without rewriting it or promising atomic rollback. The runner does not fabricate a fresh inventory import from partial readback data; reconcile seller inventory before preparing another listing change.

The official [ReviseInventoryStatus contract](https://developer.ebay.com/devzone/xml/docs/reference/ebay/ReviseInventoryStatus.html) is a narrow candidate for supported Trading-model fixed-price listings: send identifiers and price only, omitting quantity. Its response is not proof of the resulting price; use an authenticated [GetItem readback](https://developer.ebay.com/devzone/xml/docs/reference/ebay/GetItem.html). Inventory API/MIP listings require their own compatible publisher. Variations require verified exact variation identity and remain unsupported here. A SKU alone is not a substitute for the saved seller/listing/variation identity.

Before live delivery, #31 still requires the authenticated listing-origin/capability adapter and explicit live approval UI to be connected and verified against a separately approved concrete plan. The adapter must fingerprint all protected listing fields and send only identifiers, price and correlation ID; it must not send quantity, title, shipping or offer settings. A definitive rejection must mean no change was applied; partial or uncertain responses map to unknown. The Trading API has no documented compare-and-swap precondition for this price update, so read-then-write cannot promise protection against every concurrent external edit; surface this limitation in the live workflow and verify protected fields afterward.

No automatic cohort can publish through a preview. Seller OAuth/readback and the remaining publication acceptance tests, including independently approved native before/after validation, remain open prerequisites. Evidence/model gaps in #29/#30 also keep #32 automation disabled.

## Validation

`npm test` includes offline cases for exact price selection, stale evidence, identity/inventory conflicts, sold/ended items, quantities, variations, currency/shipping changes, override revisions and seller floors. `npx tsx app/features/ebay-slab-pricing/research/slabResearch.integration.test.ts` uses a disposable schema on the guarded local development database to verify concurrent immutable intents, retry mismatch rejection, persisted reload and correction invalidation with provider fetches prohibited.

Browser validation uses a clearly labeled local synthetic listing: the USD 100 to USD 125 reviewed preview survives reload, changing the reviewed ask invalidates it, and a dry run records prepared/approved/checking/completed-without-writing steps. The disposable PostgreSQL suite also exercises lost responses, restart after the write boundary, concurrent approval, cancellation, stale leases, wrong sellers, unavailable items, partial batches, terminal retries and an independently approved restore. Provider I/O is simulated; this is not a live eBay publication. Apply migrations 031/032 before this build, and restore their tables together with referenced inventory/recommendation/evidence data. Neither migration enables background work or real price writes.
