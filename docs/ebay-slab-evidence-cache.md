# Cached slab evidence

Migration `027_add_slab_evidence_refreshes.sql` adds a compact refresh table and immutable evidence revisions. It is independent of seller OAuth and inventory migration 026. Market observations retain source IDs, item IDs, event dates, unknown monetary components, correction flags, source coverage and capture dates. No account snapshots, images or raw HTTP payloads are stored. The normalized evidence itself supplies bounded diagnostic examples.

## Requests and reuse

`requestSlabEvidence` accepts at most 50 stored identities. Only confirmed identities produce requests. Identical valuation groups share eBay requests; each Alt asset shares one all-grades request across grades and physical slabs. Supply is opt-in. The request key hashes a versioned canonical specification, provider/operation, asset or valuation group, requested dates, filters, pagination and fixed marketplace/currency context. Alt remains global with reported currencies; eBay remains EBAY-US/USD. Bump the key version when changing normalization semantics.

Sales expire after six hours, supply after fifteen minutes and lazy Alt sale details after one day. Confirmed identity freshness remains governed by explicit corrections in the identity feature; it has no automatic market refresh TTL. Expiration makes evidence eligible for a requested refresh; it does not schedule repeated scraping. An unchanged warm review uses no upstream requests. Force refresh still coalesces with queued/running work. Failed refreshes keep the prior revision and expose their error/stale state; an active-search fallback cannot replace sold evidence. Failed/cancelled jobs have a ten-minute cooldown unless an operator explicitly forces a retry.

The existing native provider adapters enforce HTTP budgets and cross-process source leases. Each evidence job performs one narrow adapter operation, at most one page or detail, with up to three job attempts and the transport's bounded retries. Duplicate copies of one source event in a payload are collapsed; contradictory copies reject the payload. Independent event dates and source IDs survive. Cross-provider event reconciliation remains the pure screening work in #26, preserving both provenances instead of throwing one away during storage.

## Workers and API

The feature uses its own PostgreSQL jobs and one sequential loop rather than TCG SKU/batch jobs. A claim uses `FOR UPDATE SKIP LOCKED`, a 90-second lease, a run ID and a fresh claim ID. Restarts reuse the run ID; stale workers cannot commit or fail a newer lease. Completion inserts the immutable revision and changes the latest pointer atomically. A crash after commit cannot create a duplicate revision. Work expires terminally after three interrupted attempts. Higher-priority requests promote queued work.

Jobs have a 60-second execution signal and the underlying provider's 30-second HTTP deadline; database operations are bounded. Cancellation is checked at most every five seconds and prevents late writes immediately through the database fence. Shutdown aborts active I/O and leaves retryable work. Progress changes only on enqueue/claim/completion/failure, with attempt count, fetch duration and stale/error metadata. Idle workers poll every thirty seconds and in-process requests wake them immediately; active work keeps the provider's two-second spacing.

Development starts the loop on an evidence request. Production has a dedicated `slab-evidence-worker` entrypoint and Compose service using the existing application image and PostgreSQL. Run it separately with `npm run start:slab-evidence-worker`. It cannot consume a TCG pricing-worker slot. No new dependency, cache service or queue infrastructure is added. Production configuration was validated but not deployed.

`/api/slab-evidence` GET accepts comma-separated `keys` for statuses, or `revision` and `offset` for a fifty-observation page. POST requires same origin and a JSON body bounded to 16 KiB. Intents are `refresh` (slab IDs/window, optional supply/force), `cancel` (key/run ID), `sale-detail` (an Alt transaction from a persisted revision), and `next-page` (an eBay revision with a next page). Page/detail work is lazy. API responses contain no credentials. The UI follows in #28.

## Retention and measurements

Migration 030 adds content-addressed active-supply listing versions. New supply revisions keep a scan reference and response metadata instead of copying listing bodies; `getEvidenceRevision` reconstructs the same normalized read shape and source order. Existing inline revisions remain readable. `byte_count` continues to describe the normalized evidence size, not physical storage. Supply history keeps up to 200 recent scans per source plus protected references, and unreferenced scans expire after 180 days. Old unretained supply cache history may be evicted earlier to respect that scan bound; latest and retained revisions remain protected. Use the evidence read function rather than querying supply listing bodies directly from the revision JSON.

A normalized revision is limited to 1 MiB and 2,000 observations. Hourly compaction removes at most 500 unretained historical revisions older than thirty days. Latest revisions survive normal history compaction. Up to 100 inactive keys unused for ninety days can be removed with their unretained revisions. Recommendation creation must call `retainEvidenceRevisions` inside the same transaction as its references; retained evidence survives cleanup. Retention rechecks locked revisions to avoid racing a new reference. Future recommendation/history deletion owns release of its retained evidence; this cache does not destroy referenced audit history.

Storage scales with unique requests, refresh frequency and measured payload size, not physical stock. The live Ponyta Alt revision held 199 in-window observations in 144,933 bytes, preserving source count 214 and the sixteen-per-grade cap. Its fetch/persist run took 463 ms. eBay sold/supply revisions held 21/24 rows in 22,588/12,029 bytes and took 848/1,234 ms. Warm repeats for all three queued zero provider workflows. At these sizes, ten Alt card requests plus fifty eBay grade searches use roughly 2.6 MB per sales refresh before PostgreSQL overhead; optional supply, repeated refreshes and retained history add proportionately. These are local observations, not production guarantees.

Unit and isolated local PostgreSQL tests cover key/context changes, fifty-slab coalescing, concurrent claimers, warm hits, failure with stale evidence, lease recovery, cancellation, bounded retry/shutdown, atomic revisions, retained history and cleanup. Fifty synthetic slabs sharing ten Alt assets executed ten bounded workflows; enqueue/warm cache calls measured 7–12 ms locally. At 10,000 synthetic cache keys, PostgreSQL chose an index-only primary-key lookup (~0.1 ms). The running app returned a fifty-row page of the live 199-row Alt revision and preserved its coverage metadata.

Validation commands: `npm test`, `npm run typecheck`, `npm run build`, and `node node_modules/tsx/dist/cli.mjs app/features/ebay-slab-pricing/evidence/evidenceRefresh.integration.test.ts`. Integration tests use a disposable schema on localhost:5433 only. Adversarial passes addressed payload/request mismatches, sold-to-active fallback, property ordering after JSONB persistence, stale claim completion, shutdown losing work, retention races and idle polling footprint.
